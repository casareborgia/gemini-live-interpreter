## 3. 수정 필요 (머지 전 반드시)

### 3-1. 시작 실패 시 오류 메시지가 즉시 덮어써짐 (실측 확인)
`App.tsx` catch 블록이 `setStatusMessage('⚠️ 초기화 실패: ...')` 직후 `stopTranslationSession()` 을 호출하고,
그 함수가 다시 `'통역 세션이 중지되었습니다.'` 로 상태 메시지를 바꾼다.
브라우저에서 화면 공유 선택을 거부했을 때 사용자에게는 **실패 원인이 전혀 표시되지 않았다.**
통화 모드는 공유 선택창 취소, 오디오 공유 미체크, 지정 마이크 열기 실패가 가장 흔한 실패 경로라 치명적이다.
(기존 코드에도 같은 순서였으나, 통화 모드에서 영향이 커졌다.)
- 수정안: `stopTranslationSession(message?: string)` 으로 메시지를 인자로 받거나, 정리 후에 오류 메시지를 설정한다.

### 3-2. 부분 실패 시 수신 레코더 누수 (코드 확인)
`App.tsx` 통화 모드 시작 시 `recordersRef.current = [inboundRecorder, outboundRecorder]` 가 **두 레코더가 모두 start 된 뒤**에 실행된다.
수신(화면 공유)이 성공하고 송신(마이크)이 실패하면 catch → `stopTranslationSession()` 이 호출되지만 `recordersRef` 가 비어 있어
화면 공유 캡처가 정지되지 않는다. Chrome 의 "화면 공유 중" 표시가 남고 재시작 시 중복 캡처가 생긴다.
- 수정안: 각 레코더를 생성 즉시 `recordersRef.current.push(...)` 하거나, catch 에서 지역 변수의 레코더를 직접 `stop()` 한다.

### 3-3. 정리(cleanup) 함수가 UI 상태를 바꿈 → 개발 모드 초기 화면이 "종료됨"
`useEffect(() => () => stopTranslationSession(), [...])` 가 React StrictMode 의 이중 마운트에서 실행되어
첫 화면부터 상태 메시지가 "통역 세션이 중지되었습니다.", 두 패널 뱃지가 "종료됨"으로 표시된다 (실측).
운영 빌드에서는 발생하지 않지만, 정리 함수는 리소스만 해제하고 상태를 바꾸지 않아야 한다.
- 수정안: 리소스 해제 전용 함수와 사용자 중지 핸들러를 분리. 시작 전 뱃지는 `idle`("대기 중") 로.

## 4. 작업 보고서(WORK_REPORT) 기재 오류

1. "`git status` 깨끗 ✅" → 사실과 다름 (3절 참고).
2. 회귀·Phase 1·Phase 2 체크리스트가 모두 ✅ 로 기재되어 있으나 실제 오디오 테스트 수행 근거가 없다.
   "기존 로직 동일 유지 확인" 류의 코드 리뷰 결과를 테스트 통과로 적었다. 미수행 항목은 "미확인"으로 기재해야 한다.
3. "창(Window) 공유 시 Chrome 이 해당 창의 오디오만 분리 캡처하므로 루프가 발생하지 않는다" → **근거 없음.**
   macOS 의 시스템 오디오 공유는 시스템 전체 출력을 캡처하는 것으로 알려져 있어, 창 공유에서도 루프가 날 수 있다.
   지시서가 요구한 "실측 후 기록"이 이뤄지지 않았다. 사용자 수동 테스트 항목으로 넘긴다.

## 5. 경미한 사항 (선택)

- `App.tsx:1111` `modeButtonActive` 가 `border` 단축 속성과 `borderColor` 를 섞어 React 가 콘솔 경고를 낸다 (기존 코드).
- 장치 목록이 0개일 때(권한 차단) 안내 문구가 없다. 라벨 없음 안내는 뜨지만 목록 자체가 비는 경우도 안내가 필요하다.
- 통화 모드 설정 패널을 여는 즉시 마이크 권한 프롬프트가 뜬다 (지시서 설계대로이나 UX 상 알림 문구가 있으면 좋다).
- 백엔드 프록시: 클라이언트가 먼저 끊으면 `Cannot call "receive" once a disconnect message has been received` 오류 로그가 남는다 (기존 백엔드, 범위 밖).
